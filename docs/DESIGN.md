# The design canvas — shroom's look

**[shroom UI](https://claude.ai/artifact/FQRbQUHrumYGXtvTm6UQsg)** is the design canvas
(`https://claude.ai/artifact/FQRbQUHrumYGXtvTm6UQsg`): a Claude Design artifact with every
surface of v1 drawn as a board. It is private to Bagrat. A session reaches it through the
`Artifact` tool as him, never by fetching the URL.

It is the **look**: layout, colours, type, icons, what sits where. The
[spec](../spec/machine.json) ([readable](../spec/MACHINE.md)) remains **the behaviour and the words**: states, edges,
said-lines and laws. Where the two disagree, the spec wins on behaviour and copy and the
canvas is corrected to it. A look that bends the spec goes to the deviations in `DECISIONS.md` (as #43–#46
did). The build's calls about the canvas are DECISIONS B122.

## Design first

A new or changed UI/UX is **proposed on the canvas before any code**. That covers a
screen, a state's look, a control, a menu, or where a line or button sits.

1. Read the canvas as it is now (below). Edit the boards the change touches, or add new
   ones.
2. Publish, and tell Bagrat which boards changed and why. Wait for his yes, unless he has
   already said to go ahead and build.
3. Build to the boards. The code matches the canvas. A surprise found while building
   (a state the canvas lacks, something that won't fit) goes back to the canvas first,
   not straight into code.
4. Check it: the galleries for the webviews, the hosted Mac for what is native.

Before redrawing an existing screen, look at what the app does today. A screen often
carries more than its board (the landing page's agent prompt was missing from the canvas
once). Draw what's missing first, then change it.

## Its layout

Seven columns, side by side; each column's boards stack top to bottom. The columns are:
**Menu bar**, **Setup window**, **Library and Settings**, **The page**, **Index and
invite pages**, **Light theme**, and **The machine** (one generated overview board, below). The App icon sits above the Menu bar column.
Board titles read "Surface — state" (e.g. "Popover — paused", "The page — on its way").

from them by that file's token map, so only two light boards exist.

## The machine board, and the two lanes

**Bagrat reviews the machine in words, not on the canvas.** He says what shroom should do or
say; the sessions keep `spec/machine.json`, the code and the canvas in step behind the
scenes. Region flow boards were tried and dropped (2026-10-14): they weren't readable.

What the canvas keeps, generated from `spec/machine.json` (DECISIONS B133):

- **The machine** (`Machine.dc.html`): one overview of the six regions, their state and edge
  counts, and how many edges cross between them. Never edit it by hand: it is regenerated.
- **Said-line tags.** Each said-line a screen board shows carries its id,
  `data-said="paused.resume"`, so the JSON's words and the boards' can be held to each other.

`tools/render-machine-canvas.mjs --regions` still writes the per-region flow boards (each
state embedding its screen board, its edges and rule bands), for an agent's own look; they are
not published to the canvas.

| A change to | Goes |
|---|---|
| **Behaviour or words** (a state, an edge, a rule, a said-line) | Bagrat says it in words → a session edits `spec/machine.json` in a PR (`MACHINE.md` regenerated with it) → after it merges, the overview and the tags are brought in step → code |
| **Look only** (layout, colour, spacing, where a line sits) | Edit the screen board (design first, as above) → code. No JSON change |

**A PR that touches `machine.json`** carries what it changes, for Bagrat to read instead of
the JSON: `python3 tools/machine-diff.py` (the change list, in words; paste it in the PR
body) and `node tools/machine-picture.mjs <dir>` (a before/after picture of the regions it
touches). CI's *The machine's change list* job prints the list on the run's summary and
uploads the picture as the `machine-picture` artifact.

**After every merge that touches `machine.json`**, regenerate and publish:

1. Read `project/canvas.json` and every screen board into one `<root>` (above).
2. `node tools/render-machine-canvas.mjs <root> <short sha>` writes the overview board and
   places it in `canvas.json` (taking out any region boards).
3. `node tools/machine-said-tags.mjs <root>` reports **drift**: a tagged line whose words on
   the board differ from the JSON's. Drift is never overwritten silently — propose the
   board's words into the JSON in a PR, or put the board back. `--tag` tags new lines that
   match (a line said by several states stays untagged unless the board is its state's).
4. Publish `canvas.json`, `Machine.dc.html` and any board `--tag` changed.

## Working on it from a session

- **Read** with `Artifact` `action: "read"`, the URL above, and a `path`. The paths are
  `project/canvas.json` (the board list: x, y, w, h, title, order) and
  `project/<Board>.dc.html`, one file per board. `scope: "files"` lists them all. Save
  them into the scratchpad. A board is an `x-dc` page with inline styles; copy a
  neighbour as the template for a new one.
- **Publish** with `Artifact` and the same `url`. Pass `root` as the folder that holds
  `project/`, `file_path` as its `project/canvas.json`, and `files` mapping each changed
  board (`{"project/X.dc.html": "project/X.dc.html"}`). A new board needs both its file
  and its entry in `canvas.json`'s `boards` and `order`.
  - Read every file you send first. A publish over files you haven't read is refused, and
    so is one over a newer version: merge onto what the refusal hands back.
  - Never publish a new canvas. There is one.
- **Comments**: Bagrat leaves them on boards. `ArtifactComments` `action: "read"` lists
  the threads. One that's sent to Claude (or mentions @claude) can be answered and resolved
  there; a plain comment only reaches a session when he says so. `action: "watch"` asks to
  be woken by those; it sometimes fails at first (`mint_failed`), and a retry has worked.
- **Proving the build matches**: `npm run -s test:gallery --workspace app` and
  `gallery:pages` screenshot every state (`app/test/gallery-out/`,
  `tests/e2e/gallery-out/`). The hosted Mac (the `shroom-cloud` skill, §5) shows the real
  windows, the tray, the bubble and, with `dev/mac/camera.sh`, a camera.
