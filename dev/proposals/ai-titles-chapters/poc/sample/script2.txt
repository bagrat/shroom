Hey Jordan, welcome to the team. I made this video so you have something to come back to during your first week. I will go through four things: how the code is laid out, how to run the tests, how a change gets to production, and what being on call looks like here. Feel free to pause and try things as we go.

Let's start with the layout. Everything lives in one repository. At the top you have three folders that matter. The web folder is the customer facing app, written in TypeScript with React. The api folder is the backend service, in Go. And the jobs folder holds the small programs that run on a schedule, like the nightly export and the reminder emails. There is also a docs folder, which is honestly a bit out of date, so trust the code over the docs when they disagree. One more thing in the layout: shared types live in a package called common, and both the web app and the api read from it. If you change a type there, both sides need to build before you open a pull request.

Okay, running the tests. From the top of the repository, you run make test, and it runs everything, which takes about six minutes on a laptop. Most of the time you do not want everything. If you are working in the api, go into that folder and run go test with the package you touched, and that takes seconds. For the web app, the command is npm test, and it watches your files and reruns only what changed. There are also end to end tests that drive a real browser. Those are slow and a little flaky, so we only run them in the pipeline, not on your machine. If one of them fails on your pull request, look at the screenshot it saves before you assume your change broke it. About one in twenty failures is the test, not the code.

Now, how a change gets to production. You open a pull request against the main branch. The pipeline runs the full test suite and builds a preview copy of the web app, with its own link, so a reviewer can click around. You need one approval from someone on the team. Once it is approved and green, you merge it yourself. Merging to main deploys to staging right away. Production deploys happen twice a day, at eleven in the morning and at four in the afternoon, and the deploy bot posts in the releases channel when it starts and when it finishes. If you need something out faster, for example a fix for a customer who is blocked, ask in the releases channel and whoever is on call can push a deploy by hand. Please do not merge big changes on a Friday afternoon. Nobody will stop you, but you will be the one answering the pager on Saturday.

Which brings me to on call. Everyone on the team takes one week of on call every six weeks, and you will start after your first month, paired with someone for your first round. When you are on call, the pager app will wake you up for two kinds of alerts: the site is down, or payments are failing. Everything else waits for working hours. The first thing to open is the runbook, which is linked from every alert. It tells you what to check first and who to call if you are stuck. Do not try to be a hero at three in the morning. If you have been looking at something for twenty minutes and it is still on fire, call the backup. That is what the backup is for, and nobody will think less of you.

That is the tour. For this week, my suggestion is to get the tests running on your laptop, pick one of the small tickets marked good first issue, and take it all the way to production with a pull request. Ask me anything, any time. There are no silly questions in your first month, or honestly ever. Welcome aboard.
